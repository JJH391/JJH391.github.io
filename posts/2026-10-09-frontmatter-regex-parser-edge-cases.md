이 블로그는 `posts/`의 마크다운 파일 맨 위 `---`로 둘러싸인 frontmatter를, 별도 라이브러리 없이 `build.mjs`의 `parseFrontmatter` 함수가 정규식으로 직접 읽습니다. `package.json`의 의존성은 마크다운 파서인 `marked` 하나뿐이고, YAML을 파싱하는 라이브러리는 없습니다. 이 함수가 실제로 어떤 입력까지 처리하고 어디서 깨지는지, 코드만 읽지 않고 직접 입력을 넣어 실행한 결과로 확인했습니다.

## 파서 코드

`build.mjs` 21번째 줄부터입니다.

```js
function parseFrontmatter(raw) {
  const m = raw.match(/^---\r?\n([\s\S]*?)\r?\n---\r?\n?/);
  if (!m) return { data: {}, body: raw };
  const data = {};
  for (const line of m[1].split(/\r?\n/)) {
    const kv = line.match(/^([A-Za-z_][\w-]*)\s*:\s*(.*)$/);
    if (!kv) continue;
    let [, key, value] = kv;
    value = value.trim().replace(/^["'](.*)["']$/, '$1');
    if (/^\[.*\]$/.test(value)) {
      data[key] = value.slice(1, -1).split(',').map(s => s.trim().replace(/^["'](.*)["']$/, '$1')).filter(Boolean);
    } else if (value === 'true' || value === 'false') {
      data[key] = value === 'true';
    } else {
      data[key] = value;
    }
  }
  return { data, body: raw.slice(m[0].length) };
}
```

줄 단위로 `키: 값` 패턴을 찾고, 값이 `[...]` 형태면 쉼표로 쪼개 배열로, `true`/`false` 문자열이면 불리언으로, 그 외에는 문자열 그대로 저장합니다. 이 함수만 떼어내 여러 입력을 넣어봤습니다.

## 정상적으로 되는 것들

기본적인 경우는 그대로 작동합니다.

```js
parseFrontmatter(`---
title: 테스트 글
date: 2026-10-09
tags: [블로그, 테스트]
draft: true
---
본문
`).data
// { title: '테스트 글', date: '2026-10-09', tags: [ '블로그', '테스트' ], draft: true }
```

값 안에 콜론이 들어가도 깨지지 않습니다. 정규식이 **첫 번째 콜론까지만** 키로 보고 나머지를 전부 값으로 가져가기 때문입니다.

```js
parseFrontmatter(`---
time: 09:30:00
---
`).data
// { time: '09:30:00' }
```

콜론이 없는 줄(예: 들여쓰기된 일반 텍스트)은 `kv` 매치가 안 되면 `continue`로 그냥 넘어가므로, 파싱 자체가 멈추거나 예외가 나지는 않습니다.

빈 배열(`tags: []`)도 `filter(Boolean)` 덕분에 빈 배열 그대로 나옵니다.

## 실제로 깨지는 경우

몇 가지 입력은 의도와 다르게 처리됩니다.

**쉼표가 포함된 문자열이 배열 안에 있을 때.** 따옴표를 고려하지 않고 무조건 쉼표로 쪼개기 때문에 따옴표 안의 쉼표까지 구분자로 취급됩니다.

```js
parseFrontmatter(`---
tags: ["a, b", "c"]
---
`).data
// { tags: [ '"a', 'b"', 'c' ] }
```

의도는 `["a, b", "c"]`(두 개의 원소)였지만 결과는 세 개의 원소로 쪼개지고, 따옴표도 반쪽만 제거됩니다.

**YAML의 여러 줄 블록(`|`, `>`) 문법은 지원하지 않습니다.** 한 줄짜리 `key: value` 패턴만 읽기 때문에, 다음 줄부터 이어지는 본문은 무시됩니다.

```js
parseFrontmatter(`---
description: |
  첫째 줄
  둘째 줄
---
`).data
// { description: '|' }
```

**숫자는 숫자 타입으로 변환되지 않습니다.** `true`/`false` 두 문자열만 특별 처리되고 그 외에는 전부 문자열로 남습니다.

```js
parseFrontmatter(`---
order: 3
---
`).data
// { order: '3' }
```

**인라인 주석(`#`)을 해석하지 않습니다.** YAML에서는 `#` 뒤가 주석이지만, 이 파서는 `#`을 포함한 나머지 전체를 값 문자열로 그대로 가져갑니다.

```js
parseFrontmatter(`---
title: 테스트 # 이것은 주석일까
---
`).data
// { title: '테스트 # 이것은 주석일까' }
```

## 10-04 글의 추측을 정정: 따옴표 붙은 `"true"`는 실제로 불리언이 된다

지난 글(`posts/2026-10-04-draft-flag-build-filter.md`)에서는 코드만 읽고 "`draft: \"true\"`처럼 따옴표가 붙은 경우는 이 조건에 안 걸려서 불리언으로 변환되지 않을 수 있다"고 적었습니다. 이번에 직접 실행해보니 그 추측은 틀렸습니다.

```js
parseFrontmatter(`---
draft: "true"
---
`).data
// { draft: true }
```

이유는 처리 순서에 있습니다. 값에서 **따옴표를 먼저 제거**한 다음(`value.trim().replace(/^["'](.*)["']$/, '$1')`) 불리언 비교를 하기 때문에, 따옴표가 벗겨진 `"true"`(문자열 `true`)가 그대로 불리언 체크를 통과합니다. 반면 대소문자가 다른 `draft: TRUE`는 따옴표 제거와 무관하게 문자열 `'TRUE'`로 남습니다. 이건 10-04 글의 테스트에서도 실행 없이 코드만 보고 맞힌 부분입니다.

```js
parseFrontmatter(`---
draft: TRUE
---
`).data
// { draft: 'TRUE' }
```

정리하면, `draft` 값을 확실히 걷어내고 싶다면 대소문자(`true`)만 맞으면 되고, 따옴표를 붙이고 안 붙이고는 결과에 영향을 주지 않습니다.

## 전체 YAML 스펙과 비교하면

[YAML 1.2 스펙](https://yaml.org/spec/1.2.2/)을 구현하는 `js-yaml`이나, frontmatter 전용으로 만들어진 `gray-matter` 같은 라이브러리를 썼다면 위에서 깨진 경우들(멀티라인 블록, 인라인 주석, 숫자/날짜 타입 자동 변환, 따옴표 안 쉼표)이 전부 스펙대로 처리됩니다. 다만 이 블로그의 `posts/` 아래 실제 글 파일들의 frontmatter는 모두 한 줄짜리 `key: value`와 단순 배열만 쓰고 있어서, 현재 쓰이는 범위 안에서는 이번에 발견한 깨지는 경우들이 실제 빌드 결과에 영향을 준 적은 없습니다.

## 정리

- `parseFrontmatter`는 줄 단위 정규식 매칭으로 동작하며, 첫 번째 콜론 뒤를 통째로 값으로 가져가기 때문에 값 안의 콜론(시간 표기 등)은 문제없이 처리된다
- 배열은 쉼표로 단순 분리하므로, 원소 문자열 안에 쉼표가 있으면 의도와 다르게 더 많은 원소로 쪼개진다
- YAML의 멀티라인 블록 스칼라(`|`, `>`)는 지원하지 않고, 첫 줄의 `|` 또는 `>` 문자 자체가 문자열 값으로 저장된다
- 숫자 문자열은 숫자 타입으로 변환되지 않고 문자열로 남는다
- `#` 인라인 주석은 해석되지 않고 값의 일부로 포함된다
- 따옴표 제거가 불리언 비교보다 먼저 일어나기 때문에 `draft: "true"`도 실제로는 불리언 `true`가 된다 (10-04 글의 추측과 다른 부분)
- 현재 `posts/`의 frontmatter는 모두 한 줄 `key: value`와 단순 배열만 사용하므로, 위에서 발견한 깨지는 경우들이 실제로 발생한 적은 없다
