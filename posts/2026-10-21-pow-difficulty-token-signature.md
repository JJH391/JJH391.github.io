사이트 전체에 걸려 있던 요청 상한을 손보면서, 작업증명(PoW) 난이도를 토큰에 어떻게 담아야 하는지를 다시 확인하게 됐습니다.

## 무엇이 있었나

기존에는 사이트 전체 상한(예: 특정 동작 1분당 허용 횟수, 가입 시간당 허용 인원)에 닿으면 이후 요청을 그냥 거절하는 방식이었습니다.

이 방식에 대해 "한 명이 상한을 다 채우면 그 뒤에 오는 다른 사람이 막히는 DoS 벡터"라는 문제가 제기됐습니다. 그래서 상한에 닿으면 거절하는 대신, 최근 요청 개수에 따라 PoW(작업증명) 난이도 비트를 올리는 방식으로 바꿨습니다. 붐빌 때는 클라이언트가 더 많은 연산을 해야 요청이 통과되고, 한가할 때는 난이도가 낮습니다.

여기서 토큰 형식이 문제가 됐습니다. 기존 토큰은 `nonce.exp.sig` 구조였고, 난이도 값 자체는 서버 쪽 상수로만 존재했습니다. 난이도가 고정값일 때는 상관없었지만, 상황에 따라 난이도가 바뀌는 구조에서는 "이 토큰이 발급될 때 난이도가 몇 비트였는지"를 토큰 자체가 표현하지 못한다는 뜻이었습니다.

## 생길 수 있는 우회

난이도 값을 토큰 밖에 둔 채로 넘기는 구조를 그대로 시도하면 생기는 우회를 단위 테스트로 두 가지 확인했습니다.

1. **난이도 값 바꿔치기** — 토큰 속 난이도를 더 쉬운 값(예: 16)으로 고쳐 쓰는 경우.
2. **한가할 때 받아둔 쉬운 토큰 재사용** — 난이도가 낮은 한가한 시간에 토큰을 미리 받아뒀다가, 붐비는 시간에 그 토큰을 제출하는 경우.

## 해결

토큰 형식을 `nonce.exp.bits.sig`로 바꾸고, HMAC 서명 대상에 `bits`(발급 시점 난이도)를 포함시켰습니다. 이렇게 하면 `bits` 값을 바꾸는 순간 서명이 맞지 않아 검증에서 걸립니다.

```js
const payload = `${randomId(12)}.${Date.now() + TTL_MS}.${bits}`;
const token = `${payload}.${await hmac(env, `pow:${purpose}:${payload}`)}`;

// 검증
if (bits < await powBits(env, purpose)) {
  throw powRequired(purpose, '…', /* 새 난이도 */);
}
```

여기서 중요한 부분은 검증 시점에 "발급 시점 난이도"가 아니라 "지금 이 순간 요구되는 난이도"를 다시 계산해서 비교한다는 점입니다. 토큰에 담긴 `bits`가 지금 요구치보다 낮으면 통과시키지 않고, 428 상태 코드와 새 난이도를 돌려줘서 클라이언트가 그 난이도로 다시 계산하도록 했습니다.

이렇게 바꾼 뒤 위에서 확인한 두 가지 우회를 다시 테스트했습니다.

- 토큰 속 난이도를 16으로 고쳐 쓰는 경우 → 서명 불일치로 400.
- 한가할 때 받아 둔 16비트 토큰을 붐빌 때 사용하는 경우 → 428로 다시 계산 요구.

## 정리

- PoW처럼 난이도가 고정이 아니라 상황에 따라 바뀌는 값은, 토큰 안에 그 값을 적어 넣는 것만으로는 부족하다. 서명 대상에 포함시켜야 값 바꿔치기를 막을 수 있다.
- 토큰을 검증할 때는 "발급 시점 난이도"만 믿지 말고 "제출 시점에 요구되는 난이도"로 다시 비교해야, 한가할 때 미리 받아둔 쉬운 토큰을 붐빌 때 쓰는 것을 막을 수 있다.
- 우회 가능성을 말로만 따지지 않고 단위 테스트로 직접 재현해서 확인한 뒤 고쳤다.
