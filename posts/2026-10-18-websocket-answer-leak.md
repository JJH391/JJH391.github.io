서버 권위(server-authoritative) 구조로 만든 게임이라 "정답은 서버에만 있다"고 생각하고 있었습니다. 그런데 친구가 AI와 브라우저 개발자 도구를 써서 웹소켓 메시지만 보고 정답을 알아냈습니다.

## 무엇이 있었나

서버가 클라이언트로 보내는 웹소켓 메시지 종류(`lock`, `view` 등)를 하나씩 확인했습니다.

자물쇠 창을 열 때 서버가 보내는 `params` 안에, 놀이공원 기억력 게임의 불빛 순서 전체가 그대로 들어 있었습니다.

```
params: { L_simon: { seq } }
```

이 `seq`가 곧 정답이었습니다. 화면에 불빛을 순서대로 켜 보여주기 위해 보낸 데이터인데, 동시에 정답 그 자체였던 것입니다.

폐병원 콘셉트의 모스 전등 화면도 같은 구조였습니다. 서버는 숫자(`digits`)를 보내고 브라우저가 그 숫자를 깜빡임으로 바꿔서 화면에 표시하고 있었습니다. 모스 부호를 해독하는 과정 자체가 게임의 일부였는데, 메시지에 숫자가 그대로 있으니 해독 단계를 건너뛸 수 있었습니다.

## 원인

"화면에 그릴 재료"와 "정답"을 구분하지 않고, 렌더링하기 편한 형태로 그대로 보낸 것이 원인입니다. 기억력 게임은 불빛 순서를 그대로, 모스 부호는 숫자를 그대로 보냈습니다. 둘 다 클라이언트가 화면을 그리는 데는 필요한 데이터지만, 그 데이터 자체가 정답과 동일했습니다.

## 해결

두 화면을 각각 고쳤습니다.

**기억력 게임**: 불빛은 플레이어가 "보기"를 누를 때만 서버가 `setTimeout`으로 하나씩 순서대로 보내도록 바꿨습니다. 정답은 불빛 색만으로 알 수 없게, 판마다 바뀌는 별도 안내판의 "색 → 기호 버튼" 표와 합쳐야만 나오도록 했습니다.

**모스 부호**: 숫자 대신 깜빡임 시간표만 전송하도록 바꿨습니다.

```
on: [[시작, 끝], ...]
```

클라이언트는 이 시간표대로 불빛을 켜고 끄기만 하고, 그 깜빡임이 어떤 숫자인지는 플레이어가 직접 모스 부호를 해독해야 알 수 있습니다.

## 재발 방지: 단위 테스트

같은 종류의 문제가 다른 맵에서도 생길 수 있어서, 맵마다(200판) 자물쇠의 `params`를 영숫자만 남겨 이어 붙인 문자열에 정답 문자열이 포함되는지 검사하는 테스트를 추가했습니다.

```js
// 단위 테스트 (발췌)
const flat = (x) => JSON.stringify(x ?? null).replace(/[^0-9A-Za-z]/g, '');
for (const [id, answer] of Object.entries(P.answers)) {
  if (!LOCKS[id] || String(answer).length < 4) continue;
  assert.ok(!flat(P.params[id]).includes(String(answer)), `맵 ${m} ${id}: 자물쇠 정보에 정답이 들어 있음`);
}
```

이 테스트는 정답 문자열이 4자 이상인 자물쇠에 대해, 서버가 보내는 `params`를 평평하게 펼친 문자열 안에 정답이 그대로 나타나면 실패합니다.

## 정리

- 서버 권위 구조라도 클라이언트로 보내는 메시지 전체를 정답 노출 관점에서 다시 봐야 한다. "서버만 정답을 안다"는 것과 "클라이언트로 가는 메시지에 정답이 없다"는 것은 별개의 문제다
- 화면을 그리는 데 필요한 데이터와 정답은 분리해서 설계해야 한다. 렌더링에 편하다는 이유로 둘을 합쳐 보내면, 그 메시지를 보는 사람에게는 정답을 보내는 것과 같다
- 재발을 막으려면 사람이 코드 리뷰로 매번 확인하기보다, 맵 데이터 전체에 대해 "정답 문자열이 메시지에 포함되지 않는다"를 자동으로 검사하는 테스트를 넣는 편이 낫다
