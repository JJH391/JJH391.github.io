치트엔진류 공격에 대비해 서버 이동 검사(`onMove`) 로직을 다시 확인했습니다.

## 무엇이 있었나

이동 검사는 두 가지 값을 기준으로 삼고 있었습니다.

- 이동 여유가 `speed * dt * 1.3`씩 지속적으로 쌓인다.
- 한 번에 최대 `speed * 0.9 + 12`(약 77px)까지 허용한다.

문제는 이 허용량을 확인하는 함수 `blocked(area, x, y)`가 **도착 좌표 하나만** 검사한다는 점이었습니다. 출발점부터 도착점까지 지나가는 경로는 보지 않습니다.

타일 크기가 16px이므로, 한 번의 이동 허용량(약 77px) 안에서 4~5칸을 건너뛸 수 있는 구조였습니다. 도착 좌표만 막혀 있지 않으면, 그 사이에 책상이나 벽이 있어도 통과했습니다.

## 원인

경로를 보지 않는 검사와, 지속적으로 쌓이는 30%의 속도 여유가 함께 작용한 결과였습니다. 여유가 쌓일수록 한 번에 이동 가능한 거리가 늘어나고, 그 거리 안의 중간 지점은 검사 대상이 아니었습니다.

## 해결

경로 검사를 넣으면서 바로 걸린 문제가 하나 있었습니다. 벽 모서리를 따라 미끄러지듯 이동하는 정상적인 움직임을, 출발점과 도착점을 잇는 직선 경로로만 검사하면 오탐이 날 수 있었습니다.

그래서 세 가지 경로 중 하나라도 막히지 않으면 통과시키는 방식으로 조정했습니다.

1. 출발점에서 도착점까지의 직선 경로
2. 가로로 이동한 뒤 세로로 이동하는 경로
3. 세로로 이동한 뒤 가로로 이동하는 경로

각 경로는 4px 간격으로 점을 찍어 그 점들이 막힌 칸을 지나는지 확인합니다.

```js
function segment(ax, ay, bx, by) {
  const d = Math.hypot(bx - ax, by - ay);
  const n = Math.max(1, Math.ceil(d / 4));
  const out = [];
  for (let i = 1; i <= n; i++) out.push([ax + ((bx - ax) * i) / n, ay + ((by - ay) * i) / n]);
  return out;
}
const paths = [
  segment(r.x, r.y, x, y),
  [...segment(r.x, r.y, x, r.y), ...segment(x, r.y, x, y)],
  [...segment(r.x, r.y, r.x, y), ...segment(r.x, y, x, y)],
].filter((pts) => !pts.some(([px, py]) => blocked(p.area, px, py, w)));
if (dist > r.budget + 2 || !paths.length) { /* 거부하고 원래 위치로 */ }
```

지속 속도 여유는 30%에서 12%로 줄였습니다. 한 번에 허용하는 순간 이동량은 통신이 끊겼다가 복구될 때를 대비해 그대로 유지했습니다.

레이저, 유령, 함정 같은 다른 판정도 도착점만 보던 것을 지나온 경로 전체로 확장했습니다.

## 재발 방지

모의해킹 스크립트에 두 항목을 추가했습니다.

- 책상 너머로 한 번에 +40px 이동 시도
- 서버가 허용하는 속도의 2배로 계속 이동 시도

두 항목 모두 서버가 이동을 거부하고 원래 위치로 되돌리는 것을 확인했습니다.

## 정리

- 서버 쪽 이동 검사에서 "최대 이동 거리"와 "경로상의 충돌"은 별개의 검사다. 거리만 제한해도 경로를 안 보면 벽이나 함정을 건너뛸 수 있다
- 경로 검사를 추가할 때는 정상적인 이동 패턴(벽을 따라 미끄러지는 이동 등)에서 오탐이 나는지 같이 확인해야 한다
- 레이저, 함정처럼 "칸에 들어서면 발생하는" 판정도 이동 경로 전체를 기준으로 다시 봐야 한다. 도착 칸만 검사하면 같은 종류의 문제가 반복된다
