서버(Workers)는 시각을 UTC로 다루는데, 기능 중 하나를 한국 시간 기준 매달 1일 0시로 끊어야 하는 경우가 있었습니다. "이번 달"의 시작과 끝을 UTC 타임스탬프로 구하는 방법을 정리합니다.

## 문제

서버가 다루는 모든 타임스탬프는 UTC입니다. 그런데 "이번 달"의 기준은 한국 시간(KST, UTC+9)이어야 합니다. 그래서 단순히 UTC 기준으로 월의 시작·끝을 구하면 한국 시간으로는 하루 늦게(또는 빠르게) 경계가 잡힙니다.

필요한 것은 두 가지입니다.

- 현재 시각(UTC epoch ms)이 한국 시간으로 몇 년 몇 월인지 알아내는 것
- 그 한국 시간 월의 시작·끝을 다시 UTC epoch ms로 돌려주는 것

## 원리

한국 시간은 UTC+9이고 서머타임이 없어 오프셋이 연중 고정입니다. 그래서 임의의 UTC 타임스탬프에 9시간(32,400,000ms)을 더한 뒤, 그 값을 "UTC 기준"으로 읽으면 한국 날짜가 그대로 나옵니다. 반대로 한국 시간 기준 월의 1일 0시를 `Date.UTC`로 만든 뒤 9시간을 빼면 그 시점의 실제 UTC 타임스탬프가 됩니다.

```js
const KST = 9 * 3600_000;

export function seasonOf(ts = Date.now()) {
  const d = new Date(ts + KST);
  const y = d.getUTCFullYear();
  const m = d.getUTCMonth();
  return {
    key: `${y}-${String(m + 1).padStart(2, '0')}`,
    start: Date.UTC(y, m, 1) - KST,
    end: Date.UTC(y, m + 1, 1) - KST,
  };
}
```

`Date.UTC(y, m + 1, 1)`은 `m`이 11(12월)이어도 다음 해 1월로 자동으로 넘어가므로 연도 경계는 따로 처리할 필요가 없습니다.

## 경계값 테스트

월이 바뀌는 순간을 UTC 타임스탬프로 입력해 한국 시간 기준 월이 정확히 넘어가는지 확인했습니다.

```js
// 한국 10/31 23:59 → UTC 10/31 14:59
assert.equal(seasonOf(Date.UTC(2026, 9, 31, 14, 59)).key, '2026-10');

// 한국 11/1 00:00 → UTC 10/31 15:00
assert.equal(seasonOf(Date.UTC(2026, 9, 31, 15, 0)).key, '2026-11');
```

1분 차이로 `key` 값이 `2026-10`에서 `2026-11`로 바뀌는 것을 확인했습니다. 같은 방식으로 연도가 바뀌는 1월 초 입력에 대해서도 이전 시즌 키가 전년도 12월(`YYYY-12`)로 계산되는지 확인했습니다.

## 정리

- 서버가 UTC로 동작해도, 고정 오프셋(UTC+9)인 시간대라면 타임스탬프에 오프셋을 더하고 빼는 것만으로 해당 시간대 기준 날짜·월 경계를 계산할 수 있다
- `Date.UTC(y, m + 1, 1)`처럼 월 인덱스를 12 이상으로 넘겨도 JavaScript의 `Date.UTC`가 연도 올림을 자동으로 처리해 준다
- 월이 바뀌는 경계(23:59 / 00:00)를 정확히 겨눈 입력값으로 테스트해야 "하루 어긋남" 같은 오류를 잡을 수 있다
