계정당 대기 연결을 하나로 제한하려고, 같은 계정에서 새 웹소켓 연결이 들어오면 서버가 예전 연결을 `close(4001)`로 닫도록 구현했습니다. 그런데 로컬(`wrangler dev`) 환경에서 자동화 테스트를 돌리면 예전 연결의 `onclose`가 오지 않는 문제가 있었습니다.

## 무엇이 있었나

Cloudflare Durable Object의 Hibernation API를 쓰는 매칭 서버에서, 같은 계정으로 새 연결이 들어오면 기존 연결을 찾아 닫도록 되어 있습니다.

자동화 테스트는 "예전 연결이 종료 코드 4001로 닫힌다"를 기준으로 통과 여부를 판단했는데, 4초 안에 `onclose` 콜백이 호출되지 않아 테스트가 `null`로 실패했습니다.

별도 스크립트로 예전 연결의 상태를 확인해보니 `readyState`가 `2`(`CLOSING`)에 머물러 있었습니다. 즉 서버가 닫기 프레임을 보낸 것은 확인되지만, 닫기 핸드셰이크가 끝나 `onclose`까지 도달하는 과정이 로컬 환경에서는 완료되지 않는 상태였습니다.

## 원인

서버 쪽에서 `close(4001)`을 호출한 것은 확인했습니다 (`readyState`가 `2`로 바뀐 것이 그 증거입니다).

다만 로컬(`wrangler dev`/miniflare)과 Node `WebSocket` 클라이언트 사이에서 왜 닫기 핸드셰이크가 끝까지 진행되지 않는지는 확인하지 못했습니다. 이 부분은 원인을 특정하지 않은 채로 남겨둡니다.

## 해결(우회)

원인 자체를 해결하지는 못했기 때문에, 두 군데를 바꿔서 문제를 피했습니다.

서버 쪽에서는 연결을 닫기 전에 먼저 해당 연결의 attachment를 대기열에서 빼도록 처리했습니다. 이렇게 하면 `onclose`가 늦게 오거나 오지 않아도, 닫히는 중인 연결이 다른 매칭에 다시 쓰이지 않습니다.

```js
for (const old of this.ctx.getWebSockets(`u${user.id}`)) {
  try {
    old.serializeAttachment({
      ...(old.deserializeAttachment() || {}),
      map: null,
      since: 0,
      replaced: true,
    });
  } catch {}
  try {
    old.close(4001, 'replaced');
  } catch {}
}
```

테스트 쪽에서는 통과 조건을 "`onclose` 코드가 4001이거나, `readyState`가 2 이상"으로 느슨하게 바꿨습니다. `onclose`가 안 와도 서버가 이미 연결을 닫는 중이라는 사실만 확인되면 통과로 처리합니다.

## 확인한 방법

위 두 가지를 적용한 뒤 실제 사이트(로컬이 아닌 배포 환경)에서 같은 테스트 항목이 통과하는지 확인했습니다. 배포 환경에서는 `onclose` 코드 4001이 정상적으로 수신되었고, 대기열에서 예전 연결이 빠져 재사용되지 않는 것도 함께 확인했습니다.

## 정리

- 서버가 `close()`를 호출해 `readyState`가 `CLOSING(2)`으로 바뀌었다고 해서, 클라이언트의 `onclose`가 반드시 바로 오는 것은 아니다.
- 닫기 핸드셰이크가 끝나지 않을 가능성이 있다면, `onclose`에만 의존해 상태를 정리하지 말고 닫기를 호출하는 시점에 서버 쪽 상태(대기열, attachment 등)를 먼저 정리하는 편이 안전하다.
- 로컬 개발 환경(wrangler dev/miniflare)과 실제 배포 환경에서 웹소켓 닫기 동작이 다르게 보일 수 있으므로, 닫기 관련 테스트는 배포 환경에서도 별도로 확인해야 한다.
- 원인을 모른 채로도 증상을 우회하는 방식으로 문제를 넘길 수 있지만, 그 경우 "왜 안 되는지"는 별도로 기록해두고 추측으로 단정하지 않는 편이 낫다.
